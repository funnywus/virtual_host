# 子域名管理：操作同步与性能优化

> 范围：后台「子域名列表」相关操作（`Subdomains.vue` + `dns.js` / `nginx.js` / `subdomain-lifecycle.js` 等）  
> 目标：理清「哪些操作在同步什么、为什么慢、怎么提速」  
> 日期：2026-08-13

---

## 1. 结论（先看这个）

慢的本质不是列表 SQL，而是：

1. **远端副作用按「一站一请求 / 一站一循环」放大**（多条 SSH + 每站 `nginx -t` / `reload`）
2. **列表流量 N+1**：当前页每个站点单独 SSH 扫访问日志
3. **写操作成功后几乎都会 `loadData()`**，顺带再扫一遍流量，放大卡顿感

优化主轴应是：**按服务器批量化写配置并合并 reload**、**流量聚合/缓存**、**前端批量改单 API 并减少无谓整页重扫**。  
不要靠「无界并发」硬冲同一台 Nginx。

---

## 2. 操作清单与同步成本

| 操作 | 前端入口 | API | 是否 SSH / DNS / Nginx | 预估耗时 | 备注 |
|------|----------|-----|------------------------|----------|------|
| 列表加载 | 进入/筛选/分页 | `GET /dns/subdomains` | 仅 DB | 几十 ms | 随后触发流量加载 |
| 流量统计 | 列表自动 / 今日·近7天 | **每行** `GET .../:id/traffic` | SSH 扫日志 | 单站 0.5–5s；一页约数秒～十几秒 | 前端并发 3 |
| 添加子域名 | 添加弹窗 | `POST /dns/subdomains` | FTP + 直传脚本 + Nginx + DNS | 单站 5–30s+ | 最重单站路径 |
| 编辑子域名 | 编辑保存 | `PUT /dns/subdomains/:id` | DNS 删旧加新 | 0.5–3s | 不同步 FTP/Nginx |
| 批量生成 | 批量生成弹窗 | `POST /dns/batch-create` | 串行 N 站全套同步 | N×(5–20s) | 末尾一次 reload，但循环内 PHP fix 仍可能每站 reload |
| 续费/扣时长 | 续费 | `POST .../:id/renew` | 默认仅 DB；停用站恢复会 SSH | 快 / 2–10s | |
| 批量时长 | 批量操作 | **前端串行** N× renew | 同上 | N 倍 | 无批量 API |
| 改状态 | 状态/停用/启用 | `PUT .../:id/status` | 停用/启用写 Nginx + -t + reload | 2–15s | |
| 批量状态 | 批量设已用/未用/停用 | **前端串行** N× status | 批量停用 = N 次 reload | **日常最痛批操作之一** | |
| 备注 | 双击备注 | `PUT .../:id/remark` | 仅 DB | 很快 | 仍会 `loadData()`+流量 |
| FTP 信息 | 更多 → FTP | `GET .../:id/ftp-info` | 仅 DB | 很快 | 已按需加载，列表不带密码 |
| 检测直传 | 更多 → 检测 | `GET .../check-direct-upload` | 单次 SSH 聚合探测 | 0.5–3s | |
| 补发脚本（单） | 检测弹窗 | `POST .../deploy-upload-script` | 写脚本 + 可能 reload | 3–15s | |
| 补发脚本（批） | 顶栏按钮 | `POST .../batch-deploy-upload-script` | 按服分组复用连接；站内串行 | M×(2–10s)/服 | 每站仍可能 reload |
| Nginx 配置 | Nginx 弹窗同步 | `POST /nginx/sync/:id` | 写 conf + -t + reload | 2–10s | |
| 限流 | 限流配置 | `PUT .../:id/rate-limit` | 重生 conf + -t + reload | 2–10s | |
| 删除（单/批） | 删除 | `DELETE` / `batch-delete` | DNS；可选 SSH 清文件 | 0.5–5s/站 | 不删 nginx conf、不 reload |
| 分享 | 分享按钮 | 无 | 无 | 瞬间 | |

后台定时任务：

- **过期巡检**（`server.js` 每小时）：逐站 `disableSubdomain` → 与手动停用同成本，会和后台操作抢 SSH 池。

## 3. 典型同步链路

```
列表
  loadData
    → GET /dns/subdomains
    → loadTrafficForCurrentPage（并发 3）
         → GET /dns/subdomains/:id/traffic
         → SSH + perl 扫 /www/wwwlogs/{domain}.log[.1]

停用 / 启用
  PUT .../status
    → subdomain-lifecycle.disable/enable
    → 写 conf → nginx -t → reload（失败可能再走 HTTP fallback）

创建单站
  POST /dns/subdomains
    → createFtpUser（多条 SSH）
    → deployUploadScript（十余条命令）
    → ensureSitePhpAfterDeploy（探测 + 可能 reload）
    → 写 nginx + ensureTrafficLogFormat + fixSitePhpSock
    → nginx -t / reload
    → DNS addRecord

批量生成
  POST /dns/batch-create
    → for 每站 { 上列同步 }
    → 循环结束后再 reload 一次
    （循环内 PHP/Nginx fix 仍可能每站 reload，抵消合并收益）

批量补发脚本
  batch-deploy-upload-script
    → 按 server 分组复用 SshFtpService
    → 组内串行 deploy + fixSitePhpSock（每站可能 reload）
```

## 4. 瓶颈排序

### P0（日常必踩）

| # | 问题 | 表现 |
|---|------|------|
| 1 | 流量 N+1 SSH | 打开/翻页/几乎每次写后刷新都慢 |
| 2 | 批量停用/启用 = N 次 nginx -t/reload | 同服 20 站可达分钟级 |
| 3 | 创建/批建路径过重且串行 | 批建 10 站常需 1–3 分钟；循环内重复 reload / 重复写 traffic log_format |

### P1

| # | 问题 | 表现 |
|---|------|------|
| 4 | 批量续费前端串行，无批量 API | 选得多就线性变慢 |
| 5 | 批补发脚本每站 reload | 同服多站抖动、耗时长 |
| 6 | 过期任务串行停用 | 整点/启动时与人工操作争 SSH |
| 7 | 轻量写操作也整页 `loadData()`+流量 | 改备注也「卡一下」 |

### P2

| # | 问题 | 说明 |
|---|------|------|
| 8 | 限流/Nginx sync 整文件重生 | 单次可接受，正确性优先 |
| 9 | 批量删除串行、未按服复用；不清理 nginx | 删得相对快，但留孤儿 conf |
| 10 | `createFtpUser` 首次探测/安装 FTP | 偶发尖刺 |

## 5. 已有优化（别重复造轮）

| 机制 | 位置 | 作用 |
|------|------|------|
| SSH 连接池 | `backend/utils/ssh-connection-pool.js` | 同主机复用；`SSH_POOL_MAX_PER_HOST` 默认 5 |
| 流量前端并发 3 + token 取消 | `Subdomains.vue` | 翻页取消旧流量任务 |
| FTP 信息按需接口 | `GET .../ftp-info` | 列表不带密码 |
| 批补发按服务器分组 | `batch-deploy-upload-script` | 复用连接 |
| 批建末尾一次 reload | `batch-create` | 意图合并（部分被循环内 reload 抵消） |
| 停用不删 DNS | `subdomain-lifecycle` | 启用可快速恢复 |
| 检测直传单命令聚合 | `check-direct-upload` | 减少往返 |
| 列表服务端分页筛选 | `GET /dns/subdomains` | 避免一次拉全表 |

## 6. 优化方案与优先级

### P0（优先做）

| 方案 | 做法 | 预期收益 |
|------|------|----------|
| **批量状态 API** | `POST /dns/subdomains/batch-status`：按 `server_id` 分组；同服写多份 conf 后 **一次** `-t` + `reload`；前端批量状态改单请求 | 批量停用/启用数量级下降 |
| **流量聚合 API** | `GET /dns/subdomains/traffic?ids=&period=`；同服一批脚本扫多域名；前端一页一次请求 | 列表打开/刷新明显变快 |
| **创建/批建：推迟并合并 reload** | FTP/写文件/写 conf 先完成；PHP fix 支持 `reload:false`；批末/单站末只 reload 一次；`ensureTrafficLogFormat` 每服一次 | 批建接近腰斩；减少 Nginx 抖动 |
| **lifecycle 密码解密对齐** | 与其它路由一致使用 `decryptSecret(ssh_pass)` | 消除停用/启用失败尖刺 |

### P1

| 方案 | 做法 | 预期收益 |
|------|------|----------|
| 批量续费 API | `POST .../batch-renew`；需恢复启用的按服合并 reload | 去掉前端 N 次串行 |
| 批补发：批末统一 reload | `fixSitePhpSock` 支持 skip reload | 少 N−1 次 reload |
| 写后局部刷新 | 备注/纯 DB 续费：只更新行或 `loadSubdomains({ skipTraffic: true })` | 日常操作不再拖流量 |
| 过期任务限流 | 按服分组 + 合并 reload + 并发上限 | 避免整点卡死 SSH 池 |
| 合并小 SSH 命令 | `deployUploadScript` / `createFtpUser` 打成单条 bash | 每站少十余次 RTT |

### P2

| 方案 | 做法 | 预期收益 |
|------|------|----------|
| 流量缓存 | 内存/Redis：`domain+period` TTL 1–5 分钟 | 重复翻页接近瞬时 |
| 长任务异步化 | 批建 / 批补发脚本（含全量）→ `batch_jobs` + 进度轮询；大批量停用可后续接入 | UI 不超时、可重试 |
| 批量删除按服复用 + 可选删 nginx | 分组 SSH；批末 reload | 清理更完整且更快 |

## 7. Quick wins（1–2 天）

1. lifecycle `decryptSecret` 对齐  
2. 前端增加 `loadData({ skipTraffic })`：备注、纯 DB 续费、编辑 DNS 后跳过流量重扫  
3. `ensureTrafficLogFormat`、PHP sock 探测结果按服进程内缓存  
4. `deployUploadScript` 合并为单 shell（少 RTT）  
5. 批量状态/续费在未上批量 API 前，前端临时改为有限并发（如 3）——**仅缓解**；根治仍靠「批量 API + 合并 reload」

---

## 8. 不建议做的事

| 不要 | 原因 |
|------|------|
| 去掉 `nginx -t` 直接 reload | 坏配置可能拖垮同机所有站 |
| 无界 `Promise.all` 同机写 Nginx | 竞态、互相 -t/reload 更危险 |
| 停用改回删除 DNS | 牺牲「快速恢复」产品设计 |
| 为提速牺牲流量精度却不说明 | 大日志全量扫描贵；若改采样需标明误差 |
| 盲目加大 `SSH_POOL_MAX_PER_HOST` | 可能压垮远端；应与合并 reload 一起调 |

## 9. 推荐落地顺序

```
第 1 步  lifecycle 解密 + loadData(skipTraffic)     ← 立刻减痛
第 2 步  批量状态 API + 同服合并 reload             ← 批量停用提速
第 3 步  流量聚合 API（+ 可选短 TTL 缓存）          ← 列表体感
第 4 步  创建/批建/批补发：reload 合并 + 命令合并   ← 生成与补发提速
第 5 步  批量续费 API + 过期任务按服批处理          ← 收尾
第 6 步  （可选）长任务队列                         ← 大批量场景
```

### 已落地（2026-08-13）

| 项 | 说明 |
|----|------|
| `POST /dns/subdomains/batch-status` | 多服并行准备 → 一次 -t/reload；失败恢复全部备份，不改库 |
| `POST /dns/subdomains/batch-renew` | 并行改到期；需启用时走批量状态，失败回退到期时间 |
| `POST /dns/subdomains/traffic` | 按服并行，同服一次 SSH 扫多域名 |
| 单站停用/启用 | 先 Nginx 成功再改库；失败回退配置 |
| 批建 / 批补发脚本 | PHP fix 延迟 reload，每服末尾统一 reload |
| 前端 | 批量操作改调新 API；轻量写操作 `loadData({ skipTraffic: true })` |
| `deployUploadScript` | 十余次 SSH 合并为 **1 次** shell |
| `createFtpUser` | 建用户/权限/默认页合并为 **1 次** SSH；FTP 类型同主机缓存 10 分钟 |
| `detectPhpSock` | 探测合并 + 同主机缓存 10 分钟 |
| `ensureTrafficLogFormat` | 同主机缓存 30 分钟，批建不再每站重写 |
| 流量短缓存 | `domain → 7 日拆分` TTL 2 分钟，翻页/切今日·近7天可命中 |
| 批建 `batch-create` | 落库串行 → SSH 并发 3 → DNS 并发 5 → 统一 `-t/reload`；`-t` 失败删除本批 conf |
| 批删 `batch-delete` | DNS 并发 5 → 按服复用 SSH 清理 → 并行删库 |
| 长任务队列 | `batch_jobs` 表 + `POST /dns/batch-create` / `batch-deploy-upload-script` / `deploy-upload-script-all` 异步返回 `job_id`；`GET /dns/batch-jobs/:id` 轮询；前端进度条（批建弹窗 + 补发进度弹窗） |

## 10. 验收指标（建议）

| 场景 | 现状量级（经验） | 优化后目标 |
|------|------------------|------------|
| 打开列表（10 条，含今日流量） | 数秒～十几秒 | &lt; 2–3s（聚合后） |
| 同服批量停用 20 站 | 分钟级（20× reload） | &lt; 15–30s（1× reload/服） |
| 同服批量生成 10 站 | 1–3 分钟 | 接近腰斩，且 reload 次数 ≈ 1–2/服 |
| 修改备注 | 被流量重扫拖慢 | 瞬时更新，无流量请求 |

## 12. 一句话

> 子域名管理要快，核心不是「多开几个并发」，而是 **同服务器上的写配置合并成一次校验与 reload，列表流量改成批量查询，并避免每次小改动都整页重扫。**
